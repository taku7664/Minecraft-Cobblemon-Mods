# 상대 기술 추정 준비를 서버 주 스레드에서 분리

## 확인한 문제

2026-10-24 운영 서버의 22:30:10~50 JFR에서 Server thread의 Java 실행 표본 861개 중 420개가 상대 기술 후보 정렬 → LocalOwnStageValue → 대면 계산 → EngineRuntimeDex.readCurrent 경로에 있었다. 같은 시간대 서버는 12,389ms 밀렸지만 해당 요청의 elapsed_ms는 250이었다. 당시 JAR SHA-256은 da91fa1702ec2a5931302745b6c3401c19d04b95c0528f6576d3a76bcc68faa6이다. 표본 비율은 서버 전체 CPU 비중이나 정확한 독점 실행 시간이 아니다.

상대 기술 추정은 fallbackChain.decide 이전에 동기 실행됐다. EngineRuntimeDex의 판단별 ThreadLocal 범위는 그 뒤 LocalTacticalBrain.decide에만 적용돼, 준비 과정에서는 종족 조회마다 전체 종족 데이터 읽기·직렬화·해시를 반복했다. 전역 EngineDex 캐시를 검사하기 전에 발생하는 비용이었다.

## 변경

- 게임 액터는 요청, 상태, 카탈로그, 실제 기술 ID/노력치, 변신/일루전 정보와 Showdown 문자열을 먼저 복사한다. 게임 객체의 읽기는 기존 위치에 둔다.
- BattleBrainEndpoint의 준비 함수를 coordinator의 기존 bounded worker에서 실행한다. 추정에 전달하는 것은 위에서 캡처한 값과 액터별 추정 ledger다. worker가 battle/observationAdapter를 읽도록 옮기지 않았다.
- 준비 함수 안에서만 EngineRuntimeDex.withDecisionSnapshot 및 LocalDecisionCalculationScope.with를 연다. 같은 준비 계산의 종족 데이터는 한 번 읽으며, 끝나거나 예외가 나면 범위를 해제한다. 실제 기술의 전후 랭크 가치 계산식과 순서는 유지한다.
- 결과가 취소됐거나 준비 중 제한 시간이 끝나면 다음 Brain을 시작하지 않는다. 준비 예외는 기존 BRAIN_FAILURE/기본 AI 경로로 처리한다.
- elapsed_ms 시작을 onChoiceRequested 입구로 옮겼다. 이제 앞의 요청 준비·worker 대기·평가·서버 결과 반영 대기를 포함하는 경과 시간이다. 순수 평가 CPU 시간으로 해석하면 안 된다.
- 근사 옵션과 무관하게 적용하는 실행 경로 수정이다. 새 옵션·상수 점수·Gradle 모듈은 추가하지 않았다.
