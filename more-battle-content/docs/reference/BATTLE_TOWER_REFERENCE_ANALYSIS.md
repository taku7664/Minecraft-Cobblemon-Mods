## 1. 결론

Cobblemon Battle Tower는 단순한 전투 시작 블럭이 아니라 **팀 검증 → 팀 고정 → 연속 전투 → 난도 상승 → 보상 → 기록 → 과제**를 한 화면과 한 서버 세션에 묶은 완성형 배틀 콘텐츠다. 가장 가치 있는 참고점은 타워라는 소재나 화면 장식이 아니라 다음 네 가지다.

1. 플레이 전에 파티와 규칙을 한 화면에서 검토하고 서버에 고정하는 흐름
2. 현재 목표, 진행도, 보상과 다음 행동을 동시에 보여 주는 정보 구조
3. 싱글·더블·협동·보스가 공통 세션 수명 주기를 공유하는 구조
4. 설정, 랭킹, 과제와 가이드를 플레이 화면에 연결한 운영 구조

반대로 1.10.22 구현은 `BattleTowerManager` 4,600줄, `BattleTowerScreen` 2,690줄에 책임이 집중돼 있고, 반사 호출과 공통 21개·클라이언트 4개인 총 25개 등록 Mixin에 크게 의존한다. 구매와 일부 상태 전환에는 서버 권위·원자성·실패 복구 관점의 약점도 있다. 따라서 **동작 계약과 UX 원칙만 참고하고 구현 구조와 자산은 재사용하지 않는다.**

## 6. 런타임 구조

### 6.1 초기화

```text
Fabric entrypoint
  -> 공통 등록: 블럭/엔티티/명령/이벤트/네트워크
  -> RCT API 인스턴스 초기화
  -> 서버 시작: 설정·상점·과제 로드, 플레이어 데이터 디렉터리 준비
  -> 클라이언트 entrypoint: 렌더러·화면·S2C 수신기 등록
```

### 6.2 플레이 세션

```text
터미널 사용
  -> 서버가 화면 열기 + 전체 동기화
  -> 플레이어가 모드/레벨/전설 허용/팀 모드 선택
  -> C2S lock_in_team
  -> 서버 파티 검증 + 완전한 Pokémon 복제 스냅샷 저장
  -> C2S start_battle
  -> 솔로 시작 또는 협동/보스 매칭
  -> 아레나 예약·이동·강제 레벨·NPC/보스 생성
  -> RCT/Cobblemon 배틀
  -> 승리: 층·연승 증가, 다음 전투 가능
  -> 패배/포기: BP 정산, 스냅샷/세션 정리, 원위치 복귀
```

좋은 점은 팀 고정과 실제 배틀 시작을 분리한 것이다. 사용자는 구성을 확정한 뒤 시작할 수 있고, 서버는 두 단계에서 검증할 수 있다. 다만 현재 구현은 새 런의 `runActive`를 먼저 켠 다음 파티가 스냅샷과 같은지 검사한다. 검사가 실패하면 시작 함수가 끝나지만 런 상태는 이미 활성화될 수 있다. More Battle Content는 **모든 사전 조건 검증 후 단일 커밋으로 세션을 생성**해야 한다.

### 6.3 팀 검증

팀 고정 시 서버가 확인하는 항목은 다음과 같다.

- 기절하지 않은 포켓몬만 선택
- 모드별 최소·최대 또는 정확한 파티 수
- 동일 종 금지
- 동일 지닌 도구 금지
- 일반·보스 금지 목록
- 전설·제한 포켓몬 수
- 보스 모드에서 Mega Showdown 존재

배틀 시작 직전에는 현재 파티와 스냅샷의 포켓몬 UUID 집합, 종, 지닌 도구, 특성을 다시 비교한다. 기술, 개체값, 노력치, 성격 등은 시작 직전 비교 목록에는 없지만 스냅샷 자체는 전체 Pokémon 복제본이다. 공개 설명의 “species, held items, abilities”와 구현이 일치한다.

#### 공유 HP 구현 계약

정적 분석상 여러 플레이어를 하나의 Cobblemon 다인전 참가자 목록에 넣는 방식이 아니다. `BossInstance` 하나가 참가자별 `PokemonBattle`을 여러 개 보유하고 각 전투 ID를 같은 도전에 연결한다.

1. 각 참가자는 자신의 파티로 별도 보스 전투를 진행한다.
2. 각 전투에서 발생한 보스 피해를 해당 Showdown 보스 최대 HP에 대한 비율로 계산한다.
3. 그 비율을 월드 보스의 기준 HP로 환산해 `BossInstance.currentHealth` 하나에서 차감한다.
4. 갱신된 공유 HP 비율을 연결된 모든 전투에 다시 전송한다.
5. 한 전투의 로컬 보스 HP가 0이더라도 공유 HP가 남아 있으면 faint 처리를 취소하고 공유 HP로 교정한다.
6. 공유 HP가 0이 됐을 때만 encounter 승리 처리를 시작한다.

1~41층의 공유 HP는 기준 엔티티 HP의 15배, 이후는 20배로 설정돼 있다. 이 수치는 원본 밸런스 데이터이므로 MBC에서 복사하지 않는다. 중요한 참고점은 참가자 수와 무관한 원본 배율이 아니라 **피해 정규화, 단일 서버 권위 HP, 연결된 모든 전투에 대한 일괄 동기화** 계약이다.

#### 참가자 종료와 전체 판정

- 한 참가자의 파티만 전멸하면 그 플레이어를 탈락 집합에 넣고 동료의 전투가 끝날 때까지 대기시킨다.
- 탈락자 수가 전체 참가자 수와 같으면 전체 패배다.
- 다른 전투가 남아 있고 공유 HP가 0이면 전체 승리다.
- 한 참가자가 연결을 끊거나 직접 포기하면 남은 참가자의 상태와 무관하게 전체 도전을 실패로 종료한다.
- 승리·패배·전환 정리 과정에서는 보스와 참가 포켓몬의 일반 드롭을 막고, 남은 battle·entity·매핑을 정리한다.
- 감시 정리 로직은 참가자가 모두 오프라인이거나 전투가 생성되지 않은 채 멈추거나 도전 인스턴스가 오래 정체된 경우를 정리한다.

연결 종료 하나로 전체를 실패시키는 정책은 구현은 단순하지만 일시적인 네트워크 장애를 팀 전체에 전가한다. MBC가 보스 레이드를 구현할 때 그대로 복제할 계약이 아니라 명시적으로 다시 결정할 운영 정책이다.

#### 매칭과 단계 전환

2~3인 도전은 큐에 들어가며 다음 값이 모두 같은 참가자만 묶는다.

- 현재 층
- 강제 레벨 모드
- 전설 허용 여부
- 팀 모드
- 배틀 모드
- 목표 보스 참가자 수

2단계 보스에서는 1단계 공유 HP가 0이 되면 일반 완료로 정산하지 않고 단계 전환 상태를 만든다. 참가자별 팀 스냅샷을 보관하고 기존 전투를 닫은 뒤, 전환 지연·공지·음악·형태 연출 후 새 `BossInstance`와 2단계 전투들을 시작한다. 지연된 전투 종료와 참가자 연결 종료를 별도 추적하는 상태가 존재한다.

#### GUI와 표현

- 메인 설정 화면에서 Boss 모드와 1·2·3인 참가자 수를 선택한다.
- 팀 잠금 툴팁은 인원별 정확한 파티 수를 설명한다.
- 같은 설정의 파트너를 기다리는 상태와 5분 만료 메시지를 제공한다.
- 보스 최고 층·연승은 별도 기록 범주로 저장한다.
- 단계 전환에는 전용 공지, 음악 교체, 화면 흔들림과 일부 보스 전용 시각 효과가 있다.

장점은 참가 인원, 파티 수와 진행 목표가 명확하다는 점이다. 약점은 대기 중 현재 인원·남은 시간·매칭 키를 구조화된 화면 상태로 보여 주지 않고 채팅 메시지에 크게 의존한다는 점이다.

#### MBC에 주는 설계 경고

Boss Mode는 일반 타워전에 보스 팀 하나를 더하는 수준이 아니다. 정적 구성만 보아도 `BossInstance`, `BossMatchmaking`, 단계 보스 데이터, 공유 HP·faint·win 보정, boss AI, 도전·도주·드롭 차단, 화면 흔들림·음악·형태 전환과 복구 로직이 결합돼 있다.

- 공유 피해에는 도전 ID, 단계 상태 버전, 원본 전투 ID와 중복 방지 이벤트 ID가 필요하다.
- 참가자별 전투 종료와 전체 도전 종료를 서로 다른 상태로 관리해야 한다.
- 단계 전환은 기존 단계의 지연 패킷과 승리 콜백을 새 단계가 받지 않도록 상태 버전으로 차단해야 한다.
- 보스 규칙과 단계 전이 정의는 데이터로 두고 Cobblemon·Mega Showdown 호출은 호환 계층에 격리해야 한다.
- 음악·화면 효과 실패가 전투 상태 전이를 막아서는 안 된다.
- 보상과 기록은 encounter 결과 한 번만 정산해야 한다.
- Better AI 부재가 Boss 콘텐츠의 로드와 기본 행동 선택을 막아서는 안 된다.

따라서 MBC에서는 이를 `보스 레이드`라는 독립 PvE 기능으로 만들고, 일반 Tower 세션 관리자나 하나의 전역 화면 클래스 안에 끼워 넣지 않는다. 이전 문서의 `협동 보스전`은 같은 콘텐츠를 뜻한다.

### 6.5 일반 타워 규칙과 MBC의 차이

레퍼런스의 일반 타워는 본가 소드·실드 배틀타워를 그대로 재현한 모드가 아니다.

| 영역 | 레퍼런스 1.10.22 | MBC 확정 계약 |
|---|---|---|
| 팀 크기 | 싱글 1~6, 더블 2~6 | 서로 다른 종족 6마리 등록, 싱글 3마리·더블 4마리 선출 |
| 가방 아이템 | 빡대리님의 실제 사용 관찰상 허용. JAR의 `itemusage.json`은 층별 NPC 아이템 사용 한도를 별도로 둠 | 플레이어와 NPC 모두 전투 중 가방 사용 금지 |
| 주요 기믹 | 진행 구간이 오를수록 Tera, Dynamax와 Mega를 누적 허용 | `NONE/MEGA/DYNAMAX/TERA` 중 한 종류만 해당 전투의 양측에 허용 |
| 기믹 사용 | 여러 주요 기믹 종류가 같은 상위 구간에서 함께 활성화됨 | 각 진영은 선택된 한 종류를 전투당 최대 한 번 사용하며 종류 간 중첩 금지 |
| 진행 활용 | 기믹 누적과 NPC 아이템 사용 한도로 난도 상승 | 낮은 랭크 `NONE`, 이후 단일 기믹 프리셋을 데이터로 배치하되 정확한 랭크 매핑은 밸런스 단계에서 확정 |

공개 설명의 진행 구간 표기는 `1~5: 없음`, `5~10: Tera`, `10~15: Tera+Dynamax`, `15~30: Tera+Dynamax+Mega`, `30+: 앞선 기믹+전설`처럼 경계 층이 겹친다. 실제 경계 층에서 어느 쪽이 적용되는지는 게임 실행으로 확인하지 않았으므로 MBC 수치로 복사하지 않는다. 여기서 채택하는 것은 **진행에 따라 기믹 프리셋을 바꿀 수 있다는 발상**이며, 누적 허용과 가방 아이템 사용은 폐기한다.

## 7. 저장과 설정

### 7.1 플레이어 데이터

| 항목 | 구현 |
|---|---|
| 위치 | 월드 저장소의 `data/battle_tower/<uuid>.dat` |
| 형식 | 압축 NBT |
| 캐시 | 프로세스 전역 `Map<UUID, PlayerTowerData>` |
| 주요 필드 | 현재/최고 층, 현재/최고 연승, BP, 승패, 활성/고정 상태 |
| 모드별 필드 | 최고 층, 최고 연승, 전설 사용 여부 |
| 스냅샷 | Pokémon 전체 NBT 목록과 생성 시각 |
| 설정 | 레벨, 전설 허용, 배틀 모드, 팀 모드, 보스 참가자 수 |
| 과제 | task ID별 진행·완료·수령 상태와 데이터 버전 |

저장은 상태 변경 지점마다 직접 호출된다. 별도 임시 파일·원자적 교체·저널은 디컴파일 코드에서 확인되지 않았다. 한 플레이어 파일이 깨지면 새 기본 데이터로 폴백하므로, 운영자는 손상을 놓칠 수 있다. 새 설계는 `schemaVersion`, 임시 파일 쓰기, 원자적 교체, 실패 시 기존 파일 보존을 요구해야 한다.

### 7.2 설정 표면

| 파일 | 책임 |
|---|---|
| `config.json` | 쿨다운, 전설, NPC 기믹, 금지 종, 랜덤 팀, 돈 보상, 아레나, 가이드 |
| `bp_per_floor.json` | 일반 모드의 층별 BP 계산 |
| 보스 BP 설정 | 보스 전용 BP 계산 |
| `bp_shop_items.json` | 기본/커스텀 품목, 아이템 또는 명령 보상 |
| `itemusage.json` | 층 구간별 NPC 아이템 사용 한도 |
| `tasks.json` | 과제 추가·대체·삭제와 보상; config version 3 |
| `skins/` | 64×64 트레이너 스킨 |

과제는 내장 목록에 JSON 변경분을 합치는 방식이며, 기존 datapack 경로도 읽는다. 확장성은 좋지만 내장 기본 과제가 1,000줄가량의 코드에 하드코딩돼 있다. More Battle Content는 콘텐츠 정의를 데이터 파일에 두고 코드에는 스키마와 실행기만 남기는 편이 낫다.

## 8. 네트워크와 서버 권위 분석

### 8.1 채널 구성

| 방향 | 수량 | 주요 채널 |
|---|---:|---|
| C2S | 8 | 시작, 전체 동기화, 구매, 팀 고정, 포기, 팀 해제, 랭킹 요청, 과제 수령 |
| S2C | 14 | 화면 열기, 기본/파티/스냅샷/상점/랭킹/활동 플레이어/과제/가이드, 보스 시각·음악 효과 |

서버는 패킷 처리 본문을 서버 실행 스레드에 넘기며, 파티 고정과 배틀 시작을 서버에서 다시 검증한다. 화면에 보내는 shop·tips·tasks는 서버 설정을 기준으로 하므로 클라이언트가 운영 데이터를 임의로 정하지 못한다.

### 8.2 확인된 위험

| 위험 | 근거 | 영향 | 새 설계 요구 |
|---|---|---|---|
| 구매 수량 양수 검증 부재 | `quantity`를 그대로 `cost * quantity`에 사용하고 `spendBP`도 음수를 거부하지 않음 | 조작 패킷이 음수 BP 지출을 통해 잔액을 늘릴 가능성 | 서버 MUST `1..max` 범위를 검사하고 오버플로를 막음 |
| 장바구니 비원자성 | 클라이언트가 품목별 구매 패킷을 반복 전송 | 중간 실패 시 일부만 구매되고 UI는 카트를 비움 | 전체 카트를 한 요청·한 트랜잭션으로 처리 |
| 승인 전 낙관 갱신 | 포기·장바구니에서 로컬 상태를 먼저 지움 | 거부·지연 시 서버와 화면 불일치 | request ID와 서버 결과로만 최종 상태 전이 |
| 새 런 상태 선반영 | 스냅샷 일치 검사 전에 `startRun()` | 검증 실패에도 활성 런이 남을 수 있음 | 검증 완료 후 세션·진행 상태를 함께 커밋 |
| 블럭 위치 신뢰 | 시작 payload에 blockPos가 있으나 시작 함수에서 터미널 블럭·거리 재검증을 확인하지 못함 | 임의 좌표가 귀환·매칭 원점이 될 수 있음 | 진입 토큰 또는 서버 저장 진입 컨텍스트 사용 |
| 실패 응답 부족 | 성공 때만 전체 sync, 구조화된 오류 payload 없음 | UI가 채팅 메시지에 의존하고 pending을 해제하기 어려움 | 모든 mutation에 typed success/error 응답 |
| 정수 곱셈 | 가격×수량에 `int` 사용 | 큰 입력에서 오버플로 가능 | 상한 검증 후 `Math.multiplyExact` 또는 long 사용 |

위 항목은 정적 분석에서 확인한 경로다. 실제 공격 재현이나 운영 서버 침투 테스트는 하지 않았다.

## 9. 의존성과 Mixin 표면

### 9.1 의존 전략

- RCT API는 NPC 트레이너, 배틀 규칙, AI와 배틀 상태의 중심 의존성이다.
- Wild Battle API는 Modrinth와 메타데이터에서 필수지만, 디컴파일 코드에서는 보스 야생 전투 통합의 하부 경계에 숨어 있다.
- Mega Showdown은 선택 설치지만 보스·기믹·상점 데이터에 광범위하게 등장한다.
- CobbleDollars는 `Class.forName`과 Method 호출을 사용하는 선택 호환이다.
- Cobblemon GUI 렌더, Mega Showdown, Showdown interpreter와 BattleRegistry 내부에 반사 접근이 많다.

반사 호출은 선택 의존성 결합을 약하게 만들지만 컴파일러가 API 파손을 잡지 못한다. More Battle Content는 선택 연동마다 `IntegrationAdapter`와 존재/버전/기능 검사를 두고, 반사는 그 파일 내부에만 격리해야 한다.

### 9.2 Mixin

설정에는 클라이언트 4개와 공통 21개, 총 25개 Mixin이 등록된다. 개입 범위는 다음과 같다.

- 배틀 포켓몬과 플레이어/NPC actor
- Showdown action request와 moveset
- 기믹 사용
- 보스 피해, 체력 동기화, 승리, 도전, AI 선택과 도주
- 보스 엔티티 상호작용, 피해, 드롭
- 포켓몬 send-out과 wild state
- 카메라 흔들림과 Giratina 하늘·구름·리셋

JAR에는 설정에 이름이 없는 `BossFaintInstructionMixin`, `GraalShowdownServiceMixin`, `ShowdownInterpreterMixin` 클래스도 있다. 다른 등록 경로의 참조는 찾지 못했으므로 1.10.22에서 미사용 잔재일 가능성이 높지만, 런타임 확인 없이는 단정하지 않는다.

## 10. GUI 상세 분석

### 10.1 갤러리에서 본 화면

#### 메인 화면

- 전체 화면을 어둡게 덮고 중앙에 짙은 남색 380×260 패널을 둔다.
- 상단에는 Tower, Tasks, Leaderboard, Guide 탭과 우측 BP 배지가 있다.
- 좌측 55px 영역은 최대 6마리 파티 카드다. 포켓몬 3D 모델, 레벨, 포획 볼, 지닌 도구를 보여 준다.
- 중앙 160px 영역은 현재 층·연승·최고 기록, 10개 계단 형태의 진행도, 기믹 표시, 설정, Lock/Battle/Forfeit 버튼이다.
- 우측 150px 영역은 7개 품목이 보이는 BP 상점, 스크롤바, 장바구니 합계, Purchase/Clear 버튼이다.

#### 랭킹 화면

- Singles, Doubles, Co-op 모드 탭이 있다. 코드에는 Boss 기록도 있으나 현재 GUI selector는 세 모드만 보인다.
- Highest Floor와 Best Streak를 같은 크기의 두 열로 비교한다.
- 각 열은 상위 10명, 현재 사용자 강조, 10위 밖 사용자 별도 행, 전설 사용 `(L)`을 표시한다.

#### 가이드와 과제

- 과제는 메인 화면 내부 탭이며 한 페이지에 카드 3개와 보상 수령 버튼을 둔다.
- 가이드는 별도 화면이고 서버가 보낸 섹션을 줄바꿈해 세로 스크롤한다.
- 상단 탭 모양은 화면마다 반복 구현돼 있다.

### 10.2 코드에서 확인한 GUI 상태

| 상태 | 세부 |
|---|---|
| 고정 크기 | 논리 좌표 380×260, 화면 중앙 배치 |
| 메인 탭 | `TOWER`, `TASKS`; 랭킹과 가이드는 별도 Screen |
| 데이터 | 기본 진행, 스냅샷, 실시간 파티, 활동 플레이어, 과제, 상점 |
| 상점 | 7행, 휠·화살표·드래그 스크롤, 좌클릭 추가·우클릭 감소 |
| 과제 | 페이지당 3개 |
| 툴팁 | 화면 경계 보정, 250ms 캐시 |

2026-08-18 재확인에서 Modrinth 공식 갤러리 3장과 로컬 Fabric 1.10.22 JAR 두 사본을 다시 대조했다. 두 JAR은 SHA-256 `043EE6625CFDB796EE3C0D4210428FB2B93151D38A9FC97A1478488EB1F86F95`로 일치한다. JAR에는 볼 아이콘 외 메인 GUI PNG가 없으며, `BattleTowerScreen`이 380×260 패널과 header·party·tower·shop section을 직접 그리고 `BattleTowerStyledButton`도 바닐라 버튼 텍스처 대신 사각형·테두리·하이라이트를 직접 렌더링한다. 따라서 이 화면을 “기본 Minecraft 버튼에 정보만 얹은 구조”로 해석해서는 안 된다.

### 10.3 잘된 UX

1. **결정과 결과가 가깝다.** 파티, 룰, 진행, 보상과 시작 버튼을 같은 화면에서 볼 수 있다.
2. **현재 층이 시각적으로 강하다.** 숫자뿐 아니라 계단의 크기·색·광택으로 다음 목표를 보인다.
3. **잠금 상태가 명확하다.** 파티 카드가 녹색으로 바뀌고 시작 가능 상태와 연결된다.
4. **모드별 파티 조건을 버튼 툴팁으로 설명한다.** 비활성 이유를 사용자에게 돌려준다.
5. **실시간 사회적 정보가 있다.** 층 hover에 현재 해당 층을 진행 중인 플레이어를 표시한다.
6. **서버 설정이 화면을 구동한다.** 상점·과제·가이드는 서버 데이터를 받는다.

### 10.4 개선할 UX

1. **고정 380×260은 번역과 작은 화면에 취약하다.** 19개 언어인데 헤더 탭과 우측 BP가 폭을 나눠 쓴다.
2. **클릭 가능한 텍스트가 순환 선택기다.** 현재 값만 보고 다음 값과 전체 선택지를 알기 어렵다. 드롭다운·segmented control이 낫다.
3. **설정 변경이 암묵적 포기로 이어진다.** 잠금 중 전설 허용, 배틀 형식, 보스 인원 변경이 포기 요청을 보낼 수 있다. 파괴적 동작은 확인 대화상자가 필요하다.
4. **상점이 플레이 정보와 같은 밀도를 차지한다.** 모든 배틀 콘텐츠에 상점이 필요한 것은 아니다.
5. **대기·매칭·서버 승인 상태가 보이지 않는다.** 더블 클릭과 지연 응답을 다루기 어렵다.
6. **hover 상태를 렌더와 입력 사이에 공유한다.** 입력 영역을 독립된 widget/layout 결과로 관리하는 편이 안전하다.
7. **키보드·컨트롤러 포커스가 사실상 없다.** 커스텀 드로잉과 직접 좌표 입력만 사용한다.
8. **색상 의존도가 높다.** 활성·잠금·등급이 색뿐 아니라 아이콘과 텍스트로도 전달돼야 한다.

### 10.5 홀로그램 렌더링 구현 확인

레퍼런스의 홀로그램은 전용 셰이더 하나로 완성하는 방식이 아니라 모델·텍스처와 커스텀 정점 처리의 혼합이다.

| 대상 | 정적 자산 | 코드 효과 |
|---|---|---|
| 터미널 본체 | `holo_battle_tower.json`, `tower_terminal.png` | 일반 블럭 모델 |
| 터미널 위 타워 | `tower.json`, `tower.png` | `HoloBattleTowerRenderer`가 블럭 위에서 별도 렌더링 |
| 전투 트레이너 | 플레이어 모델, 기본 9개 또는 사용자 64×64 스킨 | `BattleTowerTrainerRenderer`가 청록색 틴트와 반투명 적용 |

- `HoloBattleTowerRenderer`는 커스텀 `VertexConsumer`에서 파랑과 분홍 사이 색을 시간에 따라 보간한다.
- 정점 Y 좌표와 시간의 사인값으로 밝기와 알파를 바꿔 수평 스캔·맥동처럼 보이는 효과를 만든다.
- JAR에는 이 효과를 위한 별도 셰이더 리소스가 없다.
- 트레이너 렌더러는 원래 스킨 색을 일부 남기고 청록색을 강하게 섞으며 알파 0.5로 렌더링한다.

MBC는 위 시각 결과만 참고한다. 원본 모델·텍스처·스킨·정점 처리 수치와 코드 구조는 복사하지 않는다. 첫 MBC 홀로 터미널은 실제 상호작용 블럭 위에 독자적인 반투명 기하를 코드로 생성해 전용 PNG와 Blockbench 모델 없이 구현한다. 애니메이션 값은 정점마다 현실 시간을 다시 읽지 않고 게임 시간과 프레임 보간값에서 렌더 단위로 계산한다.

## 11. More Battle Content 공통 GUI 설계

배틀타워, 배틀팩토리, 플레이어 1대1 PvP와 보스 레이드가 콘텐츠 범위로 확정됐고 구현 순서도 이 순서로 확정됐다. 진입은 코드 생성 홀로 터미널과 명령어를 함께 제공하며, 아래는 두 진입 경로와 네 콘텐츠가 공유할 **Battle Hub 셸 계약**이다.

### 11.1 정보 구조

```text
┌─────────────────────────────────────────────────────────────┐
│ More Battle Content     서버 상태 / BP 잔액·시즌 슬롯      │
├──────────────┬──────────────────────────┬───────────────────┤
│ 파티         │ 콘텐츠·진행              │ 상세·보상          │
│ 1 [모델]     │ Play / Challenges /      │ 선택 콘텐츠 설명   │
│ 2 [모델]     │ Records / Guide           │ 규칙·제한·보상      │
│ ...          │ 카드/경로/세션 상태       │ 오류·경고           │
│ 6 [모델]     │                          │ 확장 패널           │
├──────────────┴──────────────────────────┴───────────────────┤
│ 뒤로       설정       팀 확정       시작/대기/취소          │
└─────────────────────────────────────────────────────────────┘
```

### 11.2 화면 계약

- 화면은 특정 블럭 좌표를 필수 생성자 인자로 가져서는 안 된다.
- 홀로 터미널과 명령어는 모두 서버 발급 `entryContextId`로 화면을 열어야 한다. 터미널 문맥은 검증된 블럭 위치를 포함할 수 있지만 명령어 문맥은 물리적 블럭을 요구하지 않는다.
- Play, Challenges, Records, Guide는 공통 탭 후보이며, 콘텐츠가 제공하지 않는 탭은 숨기거나 명시적 비활성 사유를 보여야 한다.
- BP 잔액은 공통 셸에서 확인할 수 있어야 한다. 상점 패널은 첫 화면 범위와 콘텐츠 문맥에 따라 노출한다.
- Better AI는 별도 화면을 소유하지 않는다. 필요하면 본체가 읽기 전용 AI 제공자 상태 배지와 설명만 표시할 수 있다.

### 11.3 권장 상태 기계

```text
LOADING
  -> READY_UNCONFIGURED
  -> READY_INVALID
  -> READY_VALID
  -> TEAM_LOCK_PENDING
  -> TEAM_LOCKED
  -> START_PENDING
  -> MATCHMAKING 또는 ACTIVE
  -> COMPLETED / FAILED / CANCELLED
```

- 클라이언트는 서버 응답 없이 `TEAM_LOCKED`, `ACTIVE`, `COMPLETED`로 전이해서는 안 된다.
- 모든 변경 요청은 `requestId`, 예상 상태 revision과 함께 보내야 한다.
- 서버 응답은 성공 여부, 새 revision, 사용자 메시지 key, 필드별 오류를 반환해야 한다.
- 중복 `requestId`는 같은 결과를 반환하거나 안전하게 무시해야 한다.
- 취소·포기처럼 진행을 잃는 동작은 예상 손실을 보여 주는 확인 단계를 거쳐야 한다.

### 11.4 레이아웃과 접근성

- 최소 화면에서는 3열을 2열 또는 단일 열로 접고 각 영역에 스크롤을 제공해야 한다.
- 실제 문자열 폭으로 탭과 버튼을 배치하고 임의 축소 글꼴을 기본 해결책으로 쓰지 않아야 한다.
- 모든 조작은 mouse, keyboard focus, Enter/Space, Escape 또는 명시적 Back으로 가능해야 한다.
- 상태는 색상 + 아이콘 + 텍스트 중 최소 두 방식으로 전달해야 한다.
- 포켓몬 모델 렌더 실패 시 종 아이콘 또는 텍스트 카드로 기능이 유지돼야 한다.
- tooltip은 보조 설명이어야 하며 필수 오류는 화면 본문에도 남아야 한다.

### 11.5 구현 경계

| 모듈 | 책임 |
|---|---|
| `client.gui.shell` | 공통 프레임, 반응형 layout, 탭, 포커스 |
| `client.gui.party` | 읽기 전용 파티 카드와 검증 표시 |
| `client.gui.content` | 콘텐츠별 카드·진행 renderer 등록 |
| `client.state` | immutable screen state, revision, pending request |
| `network.dto` | 직렬화 가능한 화면 DTO와 mutation result |
| `server.session` | 검증 후 세션 원자 생성·전이 |
| `server.content` | 콘텐츠 capability와 규칙 제공 |
| `server.transaction` | 보상·구매·수령 원자 처리 |

메인 화면 클래스는 네트워크 송신, 서버 규칙 계산, 저장을 직접 수행해서는 안 된다. 화면은 view state를 렌더하고 사용자 intent를 controller에 전달하는 역할만 맡는다.

## 12. 채택·변형·폐기 결정

### 12.1 채택

- 설치 가능한 홀로 배틀 터미널과 명령어의 동등한 기능 진입
- BP 통화, 거래 이력, 콘텐츠 보상 정산과 서버 데이터 기반 상점
- 팀 미리보기 → 서버 검증 → 팀 확정 → 배틀 시작의 단계적 흐름
- 현재 목표와 누적 기록을 함께 보여 주는 진행 시각화
- 모드별 파티 조건과 비활성 이유의 즉시 표시
- 서버 설정 기반 가이드·과제·보상 표시
- 모드별 랭킹과 현재 사용자 위치 표시
- 스냅샷과 시작 직전 재검증이라는 서버 계약
- 1~3인 정확한 파티 분할, 서버 권위 공유 HP와 선택적 다단계 전환을 가진 Boss Mode 핵심 경험

### 12.2 변형

- 고정 타워 계단은 콘텐츠가 제공하는 일반 `ProgressTrack`으로 바꾼다.
- 레퍼런스 터미널 자산은 복사하지 않고 실제 블럭 위에 전용 모델·텍스처 없는 코드 생성 홀로그램을 렌더링한다.
- 블럭 좌표를 클라이언트 요청에서 신뢰하지 않고 서버가 검증한 터미널 또는 비블럭 진입 컨텍스트로 바꾼다.
- 유동 파티 크기는 본가형 6마리 등록·싱글 3마리/더블 4마리 선출로 바꾼다.
- 누적 주요 기믹은 랭크가 선택한 단일 기믹 규칙으로 바꾼다.
- BP 상점은 본체 공통 경제와 카트 전체 원자적 거래로 바꾼다.
- 세 화면의 반복 헤더는 공통 셸 widget으로 바꾼다.
- 순환 텍스트 선택은 전체 선택지가 보이는 control로 바꾼다.
- 채팅 기반 오류는 화면 내 typed error로 바꾼다.

### 12.3 폐기

- 원본 Holo Tower 모델·텍스처·레시피의 직접 복제
- “타워”를 본체의 기본 진행 은유로 고정하는 설계
- 원본 화면의 픽셀 배치, 색상값, 장식, 애니메이션 직접 복제
- 원본 팀 목록, 보스 순서, 커스텀 기술, 번역, 스킨, 볼 아이콘, 음악
- 4,600줄 전역 관리자와 2,690줄 화면 구조
- 광범위한 반사와 Mixin을 정상 결합 방식으로 쓰는 설계
- 클라이언트 낙관 갱신과 품목별 구매 패킷
- 전투 중 가방 아이템 사용과 여러 주요 기믹 종류의 동시 허용

## 13. 클린룸 경계

Modrinth의 라이선스 표시는 ARR이며 프로젝트 API에 공개 소스 URL이 없다. “모드팩에 넣어도 된다”는 공개 문구는 재사용·재배포 가능한 소스 라이선스를 뜻하지 않는다. 이 문서는 법률 판단이 아니라 프로젝트의 보수적 엔지니어링 정책을 정한다.

- 원본 JAR, 디컴파일 소스와 자산은 분석 증거로만 사용한다.
- 원본 클래스·메서드 단위 구현을 옮기거나 번역해 재작성하지 않는다.
- 기능은 이 문서의 외부 동작 계약에서 독립적으로 다시 설계한다.
- 원본 팀·보상 수치와 보스 편성은 새 데이터의 초깃값으로 쓰지 않는다.
- 원본 스크린샷을 새 모드의 배포 자산이나 UI texture로 쓰지 않는다.
- 구현 PR에는 원본 디컴파일 산출물을 넣지 않는다.
- 유사 기능을 구현할 때 테스트는 원본 코드가 아니라 More Battle Content의 새 계약에서 작성한다.

## 15. 분석 한계

- 실제 Minecraft 클라이언트를 실행해 화면 크기, 키보드 조작, 지연, 멀티플레이 매칭을 재현하지 않았다.
- Modrinth 공식 설명과 갤러리 원본은 확인했으나 로그인된 대화형 브라우저 세션에서 페이지 UI를 직접 조작하지는 않았다.
- Boss Mode는 공식 설명·리소스·바이트코드로 교차 확인했지만 실제 2~3인 게임을 실행하지 않았으므로 동시 피해, 지연, 단계 전환과 연결 종료의 런타임 체감은 미검증이다.
- 디컴파일 결과의 Minecraft 이름은 intermediary 난독화 상태라 일부 메서드 의미를 호출 문맥으로 해석했다.
- NeoForge JAR은 분석하지 않았다.
- 운영 서버의 생성 설정과 월드 NBT는 존재하지 않아 확인하지 않았다.
- 정적 분석으로 찾은 위험은 재현 테스트 전까지 취약점 확정 보고가 아니라 구현상 위험으로 취급한다.
