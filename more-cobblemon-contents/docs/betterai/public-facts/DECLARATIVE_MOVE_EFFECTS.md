## 1. 결정

- 본체의 Cobblemon 1.7.3 호환 계층은 Cobblemon이 함께 배포한 Showdown `data/moves.js`에서 정적으로 선언된 기술 효과를 공개 후보 사실로 제공해야 한다(MUST).
- 이 자료는 JavaScript를 실행하지 않고 객체 리터럴의 지원 속성만 읽어야 한다(MUST). 콜백 본문을 평가하거나 실행 중인 Showdown 상태를 조회해서는 안 된다(MUST NOT).
- 첫 지원 범위는 회복, 흡수, 반동, 상태이상, 휘발성 상태, 랭크 변화, 사용자·대상 교체, 방어, 사이드·필드 조건, 날씨, 지형, 연속 공격, 레벨·고정 피해, 자폭, 충전과 재충전이다(MUST).
- 효과마다 대상, 선언된 조건부 확률, 식별자, 비율·횟수 범위와 랭크 변화를 구조화할 수 있다(MAY).
- 공개 효과는 합법 후보의 설명 자료이며 후보를 삭제·정렬하거나 Router 호출을 생략하는 근거가 되어서는 안 된다(MUST NOT).

## 2. 불완전성과 덮어쓰기

- 첫 구현의 효과 범위는 항상 `DECLARATIVE_PARTIAL`로 표시해야 한다(MUST). 목록에 없는 효과를 불가능하다고 해석해서는 안 된다(MUST NOT).
- 지원하지 않는 콜백이나 조건 객체가 있는 기술은 `scriptedBehavior`를 표시하고 `MOVE_EFFECTS` 불확실성을 유지해야 한다(MUST).
- 효과 확률은 기술이 해당 효과 단계까지 도달했다는 조건부 값이다. 명중, 면역, 특성, 필드와 실패 조건까지 합친 최종 성공 확률로 표현해서는 안 된다(MUST NOT).
- 같은 기술 ID에 런타임 데이터팩 스크립트가 있으면 내장 Showdown 정의가 실제 동작을 대표한다고 가정해서는 안 된다(MUST NOT). 첫 구현은 해당 후보의 내장 효과를 노출하지 않고 미확정으로 남겨야 한다(MUST).
- 내장 자료가 없거나 파싱할 수 없는 커스텀 기술은 효과를 추측하지 않고 `null`로 남겨야 한다(MUST).

## 3. Brain 경계

- 로컬 Brain과 OpenRouter Brain은 같은 구조화 효과 사실을 받아야 한다(MUST).
- 공통 계산기는 확정적으로 선언된 자기 회복량과 기본 명중률을 곱한 상태 효과 확률 같은 비판단 요약을 제공할 수 있다(MAY).
- 흡수·반동처럼 실제 피해량에 비례하는 비율은 대상 최대 HP 대비 자기 HP 변화량으로 잘못 변환해서는 안 된다(MUST NOT).
- Router 프롬프트는 선언형 목록이 불완전하고, 효과 확률이 최종 성공 확률이 아니며, 콜백이 별도로 존재할 수 있음을 명시해야 한다(MUST).
- 효용, 순위, 추천, 교체 권고와 성격 가중치를 기술 효과 자료에 포함해서는 안 된다(MUST NOT).

## 4. 검증 계약

- 회복, 상태, 부가 랭크 변화, 피벗, 연속 공격, 고정 피해, 방어, 사이드 조건과 룸 기술의 대표 표본을 실제 Cobblemon 1.7.3 내장 자료로 검증해야 한다(MUST).
- 알 수 없는 커스텀 기술은 효과가 없어야 하고, 같은 ID의 데이터팩 덮어쓰기가 있으면 내장 효과가 억제되어야 한다(MUST).
- 외부 컬렉션을 변경해도 공개 효과 스냅샷이 바뀌어서는 안 된다(MUST).
- 공개 DTO의 기존 6개·7개 인자 JVM 생성자 호환을 유지해야 한다(SHOULD).
- Router 요청에는 효과와 불완전성 표시가 포함되되 로컬 순위·추천이 추가되지 않아야 한다(MUST).

## 5. 채택하지 않은 방식

- 기술 설명 문장을 자연어로 분석하는 방식은 번역·표현 차이와 누락 때문에 채택하지 않았다.
- Showdown 콜백을 실행하거나 임의 전투 상태에서 시험하는 방식은 부작용·동시성·숨은 상태 접근 위험 때문에 채택하지 않았다.
- 콜백이 없는 기술을 완전 해석으로 표시하는 방식은 지원하지 않는 선언 속성이 남을 수 있어 채택하지 않았다.
- 데이터팩 덮어쓰기에도 기본 내장 효과를 유지하는 방식은 실제 서버 동작과 다른 사실을 Router에 제공하므로 채택하지 않았다.
