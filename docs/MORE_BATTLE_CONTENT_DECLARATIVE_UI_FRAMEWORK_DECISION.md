# MBC 선언형 UI 프레임워크와 리소스팩 후속 결정

| 항목 | 값 |
| --- | --- |
| Status | `shared` |
| Effective | 2026-09-25 |
| Updates | `MORE_BATTLE_CONTENT_GUI_UX_CONTEXT.md`, `MORE_BATTLE_CONTENT_TOWER_CUSTOM_GUI_DECISION.md`의 구현 방식 |
| Does not obsolete | 기존 화면의 정보·상태·상호작용 계약 |
| 첫 사용처 | `more-battle-content-league-challenge` |

## 1. 결정

MBC는 웹 화면처럼 구조와 스타일을 분리해 설계할 수 있는 클라이언트 전용 선언형 UI 계층 `MbcUI`를 제공한다(MUST). League Challenge는 이 계층의 첫 실제 사용처가 되며, MBC 본체가 프레임워크를 소유한다.

`MbcUI`의 공개 계약은 화면 구조, 디자인 토큰, 재사용 컴포넌트, 상태 바인딩과 사용자 의도를 표현한다. 실제 Minecraft 렌더링 구현은 교체 가능한 내부 백엔드로 둔다(MUST). 현재 Gradle에 런타임 전용으로 연결된 owo-lib `0.12.15.4+1.21`은 첫 백엔드 후보지만, 스파이크 검증이 끝나기 전에는 확정 의존성으로 취급하지 않는다.

## 2. 의도와 구현 방식의 분리

### 2.1 공개 계약

애드온은 다음 표면만 사용해야 한다(MUST).

- 제한된 선언형 화면 문서와 화면 모델
- 색, 간격, 모서리, 글자 크기, 표면과 상태 색을 나타내는 디자인 토큰
- 행, 열, 격자, 겹침, 스크롤과 반응형 분기 같은 레이아웃 원시 요소
- 패널, 버튼, 탭, 카드, 진행 표시, 배지, 알림과 빈 상태 같은 공용 컴포넌트
- 타입이 있는 화면 상태와 `select`, `confirm`, `back`, `close` 같은 사용자 의도
- 아이템, 포켓몬, 플레이어·트레이너 모델처럼 Minecraft에서만 그릴 수 있는 호스트 슬롯

애드온은 owo 컴포넌트, `GuiGraphics`, `MbcGuiStyle`, `MbcContentFrameLayout` 또는 화면별 내부 사각형 계산 타입을 직접 참조하면 안 된다(MUST NOT).

### 2.2 내부 구현

Minecraft 백엔드는 위 계약을 실제 `Screen`과 렌더 호출로 바꾼다. owo UI를 쓰더라도 owo XML과 컴포넌트 타입은 이 백엔드 내부에만 둔다. 백엔드가 접근성이나 렌더링 요구를 만족하지 못하면 공개 화면 문서를 바꾸지 않고 자체 구현이나 다른 백엔드로 교체할 수 있어야 한다(MUST).

## 3. 계층 구조

```text
화면 상태와 사용자 의도
          ↓
MbcUI 화면 문서 + 컴포넌트
          ↓
디자인 토큰 + 테마 + 리소스 ID
       ↙                 ↘
웹 미리보기 렌더러      Minecraft 렌더러
                              ↓
                    owo 후보 또는 자체 백엔드
```

각 계층의 책임은 다음과 같다.

1. **상태 모델**은 서버가 승인한 값과 클라이언트 임시 선택을 구분한다.
2. **화면 문서**는 정보 구조와 컴포넌트 배치를 선언한다.
3. **테마**는 화면 구조를 바꾸지 않고 시각 토큰과 리소스를 교체한다.
4. **웹 미리보기**는 빠른 디자인 반복과 화면 폭 비교를 담당한다.
5. **Minecraft 렌더러**는 실제 입력, 내레이션, 클리핑, 아이템·포켓몬 렌더링을 담당한다.

## 4. 선언 문서

첫 버전은 XML 기반의 작은 전용 문법을 사용한다(SHOULD). 브라우저의 임의 HTML·CSS를 그대로 실행하거나 변환하지 않는다(MUST NOT). 예시는 필드명을 확정하는 최종 스키마가 아니다.

```xml
<screen id="league_home" schema-version="1" theme="league_challenge">
  <header title="ui.league.home" close-action="close" />
  <columns collapse-below="426">
    <rank-summary bind="progress.rank" />
    <challenge-list bind="challenges" action="select_challenge" />
    <rule-summary bind="selection.rules" />
  </columns>
  <action-bar primary="start_challenge" secondary="back" />
</screen>
```

문법은 다음 제약을 가져야 한다(MUST).

- 임의 스크립트, 원격 URL, 파일 경로와 런타임 클래스 이름을 받지 않는다.
- 행동은 등록된 타입 있는 의도만 호출하며 명령어 문자열을 실행하지 않는다.
- 알 수 없는 필수 컴포넌트, 순환 템플릿과 잘못된 바인딩은 로드 때 거부한다.
- 화면 문서와 테마에는 각각 스키마 버전을 둔다.

## 5. 자체 리소스팩 계약

기본 UI는 별도 팩 설치 없이 보여야 한다(MUST). 따라서 MBC 기본 테마와 공용 텍스처는 MBC JAR의 `assets/cobblemon_more_battle_content/`에, League 전용 테마와 자산은 League Challenge JAR의 자체 namespace에 넣는다.

서버 운영자와 팩 제작자는 같은 안정적 리소스 ID를 가진 외부 리소스팩으로 시각 자산을 덮어쓸 수 있다(MAY). 이 선택형 팩은 구조나 서버 규칙을 바꾸지 않고 색, 프레임, 아이콘, 배경, 초상화와 애니메이션 프레임만 교체한다(MUST).

권장 경로는 다음과 같다.

```text
assets/<namespace>/mbc_ui/screens/*.mbcui.xml
assets/<namespace>/mbc_ui/themes/*.json
assets/<namespace>/textures/gui/mbc_ui/panels/*.png
assets/<namespace>/textures/gui/mbc_ui/icons/*.png
assets/<namespace>/textures/gui/mbc_ui/backgrounds/*.png
assets/<namespace>/textures/gui/mbc_ui/portraits/*.png
```

- 프레임과 패널은 해상도 확대에 견디는 9-slice 또는 반복 가능한 작은 텍스처를 우선한다(SHOULD).
- 한국어·영어가 모두 필요한 첫 버전은 Minecraft 기본 글꼴을 사용한다(SHOULD). 별도 글꼴은 두 언어, UI 배율과 다른 리소스팩 충돌을 검증한 뒤 추가한다.
- 누락되거나 잘못된 테마 자산은 MBC 기본 토큰과 안전한 실루엣으로 대체한다(MUST).
- 리소스 재로드는 전체 후보를 검증한 뒤 한 번에 교체하며, 실패하면 직전 정상 화면·테마를 유지한다(MUST).
- 포함 자산은 직접 제작했거나 재배포 허가와 크레딧 조건이 확인돼야 한다(MUST).

## 6. 웹 미리보기

웹 미리보기는 같은 제한된 화면 문서와 토큰을 HTML/CSS로 표현한다. AI나 디자이너가 웹 도구로 화면을 빠르게 다듬을 수 있게 하되, 별도 브라우저를 Minecraft 안에 내장하지 않는다(MUST NOT).

미리보기는 다음을 제공해야 한다(SHOULD).

- `320×240`, `426×240`, `640×360` 논리 뷰포트 전환
- 한국어·영어와 주요 상태 조합 전환
- 누락 자산, 긴 문자열과 빈 목록 상태
- 아이템, 포켓몬, 3D 모델을 위한 크기 고정 대체 슬롯
- 토큰과 컴포넌트 상태의 즉시 갱신
- 비교 가능한 정적 스냅샷 출력

웹 미리보기 합격은 게임 내 렌더링, 글꼴 폭, 포커스, 내레이션, 마우스 휠, scissor 클리핑이나 성능의 증거가 아니다(MUST).

## 7. owo 백엔드 스파이크 게이트

owo 후보는 다음 항목을 실제 Minecraft 1.21.1 개발 프로필에서 검증해야 한다.

1. 기본 owo·바닐라 표면을 노출하지 않고 MBC 텍스처와 색으로 전부 그릴 수 있는가
2. 중첩 클리핑, 세로·가로 스크롤과 작은 화면 재배치를 정확히 처리하는가
3. 키보드·게임패드 포커스, ESC, 툴팁과 내레이션을 보존하는가
4. 아이템, 포켓몬, 플레이어·트레이너 모델 호스트 슬롯을 안전하게 섞을 수 있는가
5. 리소스 재로드와 개발 중 화면 문서 갱신이 기존 화면을 손상하지 않는가
6. 대형 목록에서 프레임 시간과 입력 지연이 허용 범위인가

위 항목 중 공개 계약을 우회해야만 해결되는 문제가 있으면 owo를 최종 백엔드로 채택하지 않는다(MUST NOT). `fabric.mod.json`의 의존성 선언과 배포 방식은 백엔드 채택 뒤 별도 커밋에서 확정한다.

## 8. GUI 우선 구현 단계

### UI-0: 기준선과 스파이크

- 현행 화면과 실제 캡처를 보존한다.
- 최소 `MbcUI` 화면 문서, 토큰, 상태와 행동 모델을 테스트로 정의한다.
- 동일한 League 홈 예시를 웹과 owo 후보로 각각 렌더링한다.
- 백엔드 채택 또는 기각 근거를 후속 결정으로 기록한다.

### UI-1: 프레임워크 핵심

- 파서, 검증기, 템플릿, 토큰 병합과 안전한 폴백을 구현한다.
- 행·열·격자·겹침·스크롤과 반응형 분기를 구현한다.
- 공용 패널, 버튼, 탭, 카드, 상태 배지와 행동 디스패처를 구현한다.

### UI-2: 내장 테마와 외부 덮어쓰기

- MBC 기본 테마와 League 테마의 namespace·리소스 ID를 고정한다.
- JAR 내장 자산만으로 완전한 기본 화면을 만든다.
- 선택형 외부 리소스팩 덮어쓰기, 누락 자산 폴백과 재로드 원자성을 검증한다.

### UI-3: 웹 미리보기 도구

- Minecraft와 같은 문서를 읽는 정적 미리보기 앱을 만든다.
- 세 뷰포트와 한·영, 잠김·가능·완료·진행 중 상태 fixture를 제공한다.
- 스냅샷 차이를 검토할 수 있는 출력 경로를 만든다.

### UI-4: League 수직 단면

- 실제 서버 연동 없이 fixture 상태로 홈 → 체육관 상세 → 파티 확인 → 결과 흐름을 완성한다.
- League 전용 컴포넌트와 테마를 애드온 namespace에 둔다.
- 구조·테마·번역이 웹과 Minecraft에서 같은 의미를 유지하는지 확인한다.

### UI-5: 게임 내 승인과 백엔드 확정

- 실제 1.21.1 클라이언트에서 세 화면 폭, 키보드, 내레이션, 스크롤과 리소스 재로드를 검증한다.
- 기존 MBC 화면보다 나아졌다는 평가는 같은 상태·크기의 나란한 캡처로 한다.
- 결과를 근거로 owo 유지, 보완 또는 교체를 결정한다.

### UI-6: 연동과 점진 이행

- League의 fixture를 서버 권위 페이로드에 연결한다.
- 이후 MBC 기존 화면은 한 화면씩 선택적으로 옮긴다.
- 이행한 화면이 실제 검증을 통과할 때까지 기존 화면을 폴백으로 유지한다.

## 9. 롤백과 부분 배포

- 현재 MBC 화면을 한 번에 다시 쓰지 않는다(MUST NOT).
- 첫 구현은 개발 전용 진입점이나 명시적 실험 설정 뒤에 둔다(SHOULD).
- 새 화면 패킷은 구 클라이언트와의 부분 배포에서 디코드 충돌을 만들지 않도록 새 식별자를 사용한다(MUST).
- 화면 문서·테마 로드 실패는 서버 진행이나 전투를 중단하지 않아야 한다(MUST).
- League Challenge가 없어도 MBC와 `MbcUI`의 기본 화면이 로드돼야 한다(MUST).

## 10. 기각한 대안

| 대안 | 기각 이유 |
| --- | --- |
| owo API와 XML을 애드온 공개 계약으로 사용 | 백엔드 교체와 버전 업그레이드가 모든 애드온의 호환성 문제가 된다. |
| owo 기본 위젯 외형을 그대로 사용 | 기능 구현은 빨라도 MBC 고유 시각 언어와 리소스팩 교체 목표를 만족하지 못한다. |
| 임의 HTML·CSS를 게임에서 직접 실행 | Minecraft 입력·렌더링·보안·성능 계약과 맞지 않는다. |
| Chromium/JCEF를 게임 GUI로 내장 | 배포 크기, 플랫폼 호환성, 입력과 리소스 통합 비용이 과도하다. |
| 모든 기존 화면의 일괄 재작성 | 회귀 범위와 롤백 비용이 크고 서버 기능 개발을 장기간 막는다. |
| 기본 UI를 별도 리소스팩 설치에 의존 | 팩 누락 때 제품 기본 화면이 깨지고 클라이언트 설치 절차가 늘어난다. |

## 11. 완료 기준

- 하나의 League 화면 문서가 웹과 Minecraft에서 같은 정보 구조와 상태를 표현한다.
- 기본 JAR만 설치해도 완전한 화면이 보이고 외부 팩으로 시각 자산만 교체할 수 있다.
- 잘못된 화면 문서·테마·자산이 직전 정상 화면이나 게임 진행을 깨뜨리지 않는다.
- 320×240에서 필수 행동을 잃지 않고, 426×240과 640×360에서 불필요한 빈 공간을 만들지 않는다.
- 한·영, 키보드 탐색, 내레이션과 마우스 스크롤을 실제 게임에서 확인한다.
- owo 채택 여부가 스파이크 증거와 함께 별도 결정으로 남는다.
