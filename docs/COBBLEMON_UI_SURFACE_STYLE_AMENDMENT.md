# Cobblemon UI 표면 스타일 후속 결정

| 항목 | 값 |
| --- | --- |
| Status | `shared` |
| Effective | 2026-09-26 |
| Updates | `COBBLEMON_UI_TOOLKIT_AND_RUNTIME_EVIDENCE_AMENDMENT.md` |
| Does not obsolete | 의미 기반 버튼 크기, 입력·포커스·내레이션 계약, 내장 기본 테마와 선택형 Visual Pack 경계 |
| 적용 대상 | `cobblemon-ui-kit`과 이를 소비하는 Cobblemon 클라이언트 화면 |
| 주 독자 | 공용 위젯·테마·화면을 구현하는 개발자 |

## 1. 수정 이유

첫 공용 버튼은 폭과 글자 축척을 의미 속성으로 분리했지만, 모든 상태를 같은 직사각형 채움·1픽셀 테두리·좌측 강조선으로 그렸다. 이 구조는 화면마다 필요한 외곽 형태와 표면 깊이를 표현하지 못하고, 테마를 바꿔도 버튼들이 같은 부품처럼 보이는 문제를 남긴다.

첨부된 Pokémon식 정보 패널에서 확인되는 가장 큰 특징은 **큰 외곽 셸의 잘린 모서리와 내부 직사각형 정보 행이 함께 존재한다는 점**이다. 따라서 모든 위젯을 비직사각형으로 만드는 것이 아니라 역할별로 서로 다른 표면을 조합해야 한다(MUST).

## 2. 표면 계약

위젯 표면은 다음 네 속성을 독립적으로 표현해야 한다(MUST).

| 속성 | 첫 안정 후보 | 계약 |
| --- | --- | --- |
| `shape` | `Rectangle`, `Chamfer` | `Chamfer`는 잘라낼 픽셀 수와 적용할 모서리를 가진다. |
| `fill` | `None`, `Solid`, `VerticalGradient` | 채움 없음, 단색, 위에서 아래로 두 색을 보간하는 채움을 제공한다. |
| `border` | `None`, `Solid` | 테두리 없음 또는 색·굵기가 있는 테두리를 제공한다. |
| `backgroundOpacity` | `0.0 .. 1.0` | 기존 채움 색의 알파에 추가로 곱한다. 테두리 알파에는 적용하지 않는다. |

임의 각도·다중 중단점 그라데이션, 둥근 벡터 경로와 셰이더 효과는 첫 구현 범위가 아니다(MUST NOT). 실제 소비 화면에서 필요가 확인된 뒤 계약을 확장한다(SHOULD).

## 3. 테마와 호출부 덮어쓰기

- 테마 스냅샷은 셸·패널·보조 패널의 표면 토큰과 버튼 종류·상태별 표면을 보유해야 한다(MUST).
- 호출자는 테마 표면 전체를 다시 작성하지 않고 `shape`, `fill`, `border`, `backgroundOpacity` 중 필요한 값만 덮어쓸 수 있다(MAY).
- 일반 화면은 호출부 덮어쓰기보다 `PRIMARY`, `SECONDARY`, `DANGER`, `GHOST`, `ICON`의 의미 스타일을 우선 사용해야 한다(SHOULD).
- `GHOST`의 기본 표면은 테두리 없는 상태를 실제 `None`으로 표현해야 한다(MUST). 투명색 테두리를 전달해 “없는 것처럼” 처리하지 않는다.
- 모든 버튼 종류에 같은 챔퍼, 같은 그라데이션과 같은 장식선을 적용하면 안 된다(MUST NOT).

기본 테마는 다음 차이를 제공한다(SHOULD).

- 큰 셸: 네 모서리 챔퍼, 어두운 세로 그라데이션, 두꺼운 밝은 테두리
- 일반 패널: 작은 챔퍼 또는 직사각형, 낮은 대비의 채움
- Primary·Danger: 서로 다른 모서리 조합의 챔퍼와 상태별 그라데이션
- Secondary: 작은 챔퍼 또는 단색 표면
- Ghost: 테두리 없음, 상태에 따라 투명하거나 낮은 불투명도의 채움
- Icon: 작은 전방향 챔퍼

## 4. 렌더링과 입력 경계

- 표면 렌더러는 모양에 맞춰 채움·그라데이션·테두리를 그려야 한다(MUST).
- 포커스 상태의 테두리도 직사각형 외곽선으로 되돌아가면 안 되며 현재 모양을 따라야 한다(MUST).
- 첫 `Chamfer`는 작은 장식 컷만 허용하고, 접근 가능한 클릭 영역은 기존 직사각형 히트박스를 유지한다(MUST). 잘린 모서리 부분도 클릭되는 것이 현행 의도다.
- 큰 컷이나 오목·자유형 모양을 추가할 때는 시각 모양과 히트 테스트가 달라지지 않도록 별도 다각형 입력 계약을 먼저 정의해야 한다(MUST).

이 입력 결정은 작은 장식 컷에서 클릭 목표가 줄어드는 것을 막는다. 다만 시각적으로 비어 보이는 큰 영역까지 클릭되는 형태에는 사용하면 안 된다(MUST NOT).

## 5. 코드와 리소스팩의 역할

첫 구현은 자산이 없어도 동작하는 코드 렌더 폴백으로 제공한다(MUST). 후속 Visual Pack은 같은 의미 토큰에 sprite 또는 nine-slice 자산을 연결할 수 있지만(MAY), 모양·상태·입력 계약을 바꾸면 안 된다(MUST NOT).

리소스팩만으로 이 요구를 해결하지 않는다. 리소스팩은 시각 자산을 공급하지만 `border = None`, 불투명도, 상태별 선택과 히트박스 의미를 소유할 수 없기 때문이다.

## 6. 검증 게이트

1. 순수 단위 테스트에서 챔퍼 행의 좌우 범위, 선택 모서리, 잘못된 컷·테두리 굵기·불투명도를 검증한다(MUST).
2. 기본 테마에서 큰 셸, Primary, Secondary, Ghost가 같은 표면 계약으로 붕괴하지 않았음을 검증한다(MUST).
3. Component Gallery에서 테마 기본 스타일과 호출부 덮어쓰기 예시를 함께 보여야 한다(MUST).
4. 실제 월드에서 이전 캡처와 새 캡처를 나란히 비교하고, 외곽 셸·버튼·내부 정보 행의 차이를 기록한다(MUST).
5. 빌드나 캡처 자동화는 물리 마우스 입력, 화면 읽기 프로그램 출력 또는 실제 소비 모드 통합을 증명하지 않는다(MUST NOT).

## 7. 기각하거나 보류한 대안

| 대안 | 상태 | 이유 |
| --- | --- | --- |
| 모든 위젯에 같은 대각선 모서리 적용 | 기각 | 모양만 바뀐 동일 부품 반복이며 정보 계층을 만들지 못한다. |
| 화면마다 원시 `fill` 좌표를 직접 작성 | 기각 | 테마 교체와 상태 일관성을 잃고 같은 렌더 로직이 복제된다. |
| 리소스팩만으로 해결 | 기각 | 입력·상태·불투명도·테두리 유무 계약을 제공하지 못한다. |
| 처음부터 임의 각도 셰이더 그라데이션 제공 | 보류 | 현재 요구는 세로 그라데이션으로 충족되며 API와 렌더 비용을 먼저 늘릴 근거가 없다. |
| 챔퍼 시각 모양 그대로 다각형 히트 테스트 | 보류 | 작은 장식 컷에서는 클릭 영역과 접근성만 줄어든다. 큰 컷 사용처가 생기면 별도 계약으로 추가한다. |
