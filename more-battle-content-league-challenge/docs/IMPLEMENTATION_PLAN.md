# 구현 계획

## 1. 계획 원칙

League Challenge는 Cobblemon 공용 위젯 프레임워크의 위험을 Component Gallery와 실제 월드에서 먼저 제거한 뒤 서버 진행과 전투를 연결한다. 기존 두 League 홈 스파이크는 타이틀 화면 개발 fixture 비교 자료이며 실제 월드 승인이나 위젯 체계 완료 증거가 아니다.

- 독립된 Cobblemon UI 툴킷 소스 모듈이 위젯·테마·입력 계약을 소유하고 League Challenge와 Battle UI가 첫 소비자가 된다(MUST).
- 기본 UI 자산은 MBC·League 각 JAR에 내장한다(MUST).
- 외부 Visual Pack은 허용된 cosmetic 토큰과 시각 자산만 선택적으로 덮어쓴다(MAY).
- 화면 구조, 행동 ID, 확인 단계와 포커스 순서는 타입 있는 코드가 소유한다(MUST).
- 기존 MBC 화면을 한 번에 다시 쓰지 않는다(MUST NOT).
- 웹 미리보기는 Minecraft 화면 안정화 뒤 선택하는 비권위 보조 도구이며 게임 내 검증을 대신하지 않는다(MUST NOT).
- 서버 권위, 진행 저장과 전투 기능은 GUI 설계와 독립적으로 테스트한다(MUST).

## 2. GUI 착수 전 결정 게이트

GUI 단계는 다음 가정으로 시작할 수 있으며, 서버 기능의 미결정 항목 때문에 막지 않는다.

1. 첫 fixture는 신오 Pt 기반 8개 체육관과 사천왕·챔피언 구조를 사용한다.
2. 레벨캡 숫자와 실제 팀은 임시 표시값이며 제품 계약으로 고정하지 않는다.
3. 뱃지 이미지는 임시 원본 아이콘 또는 자리표시자를 사용하며 제3자 원본 게임 자산을 넣지 않는다.
4. owo-lib `0.12.15.4+1.21`은 Minecraft 백엔드 후보일 뿐 최종 채택이 아니다.
5. 첫 테마 미술 방향은 Component Gallery와 실제 월드 League 홈을 본 뒤 빡대리님이 확정한다.

다음 항목은 서버 연동 단계 전에 실제 환경에서 확정하거나 검증해야 한다.

1. Cobblemon 1.8.1에서 사용할 개인별 레벨캡 모드와 API
2. 뱃지별 정확한 레벨캡 숫자
3. 서버당 단일 활성 리그인지 다중 리그인지
4. 사천왕 연속 도전 중 접속 종료·서버 재시작 처리
5. 연속 도전 중 가방 아이템 사용 규칙
6. 진행 중 Tower·Factory 런에 잠금 정책을 적용하는 시점
7. PokeBadges 대상 버전, 모드 ID, 실제 뱃지 식별자
8. 레벨캡 초과 포켓몬의 경험치·진화·복종·전투 참가 처리 의미

## 3. GUI 우선 단계

### 0단계: 실행 가능한 GUI 개발 기반

- League Challenge를 Gradle 모듈로 먼저 포함
- 서버·클라이언트 진입점, 모드 메타데이터와 한·영 번역 추가
- 개발 환경에서만 fixture 화면을 여는 진입 경로 추가
- PokeBadges 실제 버전·모드 ID·API 확인 전에는 필수 의존성을 추측하지 않음
- 진행 저장, 레벨캡, 터미널, 전투와 시설 잠금은 이 단계에 넣지 않음

완료 조건: 새 모듈이 MBC와 함께 컴파일되며 개발 진입점이 배포 환경에는 등록되지 않고, 롤백 시 저장 데이터가 남지 않는다.

### 1단계: 실험적 타입 MbcUI 계약

- 현행 MBC 화면·캡처와 화면별 정보 계약을 기준선으로 보존
- League 홈의 타입 있는 화면 모델, 컴포넌트, 상태 바인딩과 행동 ID 정의
- 중복 컴포넌트 ID, 등록되지 않은 행동과 잘못된 상태를 거부하는 테스트
- 화면 구조와 행동을 `ResourceManager`에서 읽지 않는 경계 테스트
- 외부 범용 XML·JSON 화면 문법은 구현하지 않음
- 안정 패키지가 아닌 명시적 experimental 계약으로 제공

완료 조건: 실험 계약이 owo 타입을 노출하지 않고 리소스팩이 화면 구조·행동·확인 단계를 교체할 수 없다. 최소 두 화면 반복 전에는 안정 API로 승격하지 않는다.

### 2단계: 타이틀 화면 백엔드 비교 스파이크

- 같은 League 홈 fixture를 현재 MBC 코드 드로잉 방식과 owo 후보 방식으로 각각 최소 구현
- 클리핑, 스크롤, 반응형 배치, 키보드·내레이션과 3D 호스트 슬롯 확인
- `320×240`, `426×240`, `640×360`의 같은 상태를 나란히 캡처
- 구현량, 예외 처리와 시각 차이 기록
- 주입된 입력과 물리 입력, 타이틀 fixture와 실제 월드 증거를 구분해 기록

완료 조건: 두 후보가 커스텀 표면을 그릴 수 있는지와 세 폭·한영·클리핑 차이가 타이틀 fixture 증거로 남는다. 이 단계에서 백엔드를 최종 선택하지 않는다.

### 3단계: Cobblemon UI 툴킷과 Component Gallery

진행 상태: 버튼·테마·선택·데이터·레이아웃·오버레이 위젯과 League용 본문·패널·단계·순서형 선출·렌더 슬롯, 실제 Cobblemon 월드 갤러리 기준선까지 구현했다. 외부 cosmetic 테마 검증, 전역 행동 디스패처와 대형 목록 가상화는 남아 있으므로 단계 전체 완료로 표시하지 않는다.

- 독립 Gradle 클라이언트 소스 모듈과 내부 렌더러 분리
- 행·열·격자·겹침·스크롤·반응형 레이아웃
- 내용 폭·채움·고정 폭과 variant·size·아이콘·보조 문구를 가진 버튼 계열
- 패널, 탭, 카드, 목록, 스크롤, 선택 카드, 상태 배지, 알림과 행동 디스패처
- 불변 테마 스냅샷과 위젯 상태별 sprite, 코드 기본 토큰과 누락 자산 폴백
- 허용 목록 기반 외부 cosmetic 테마 검증과 전체 테마 폴백
- 한·영 긴 문자열과 normal/hover/focus/pressed/disabled/selected를 담은 개발 전용 Component Gallery

완료 조건: League와 Battle UI의 도메인 타입 없이 갤러리가 열리고, 잘못된 외부 테마를 넣어도 코드 기본값과 화면 행동이 유지된다. 공개 API에 owo 타입이 없다.

### 4단계: 실제 월드 League 홈과 GUI 수직 단면

- League 테마와 원본 또는 명확한 임시 자산을 애드온 JAR에 내장
- 진행 저장·전투 없이 화면 열기만 담당하는 최소 개발용 터미널 블록과 서버 패킷 추가
- 터미널 블록 우클릭과 서버 패킷으로 fixture League 홈 열기
- 기존 고정 폭 행동 버튼을 공용 의미 위젯으로 교체
- 리그 홈 → 체육관 상세 → 파티 확인 → 결과 네 화면을 Minecraft에서 구현
- 계급, 뱃지, 도전 카드, 관장, 레벨캡, 파티 규칙과 해금 컴포넌트
- 두 화면 이상에서 반복된 요구만 공용 UI 툴킷 API로 승격
- 허용 목록형 `League Challenge Visual Pack` 예제로 cosmetic 덮어쓰기 확인
- 세 화면 폭과 한·영 실제 월드 검토

완료 조건: `client.level`과 `client.player`가 있는 실제 월드에서 터미널 우클릭과 서버 패킷으로 화면이 열리고, 별도 팩 없이 완전한 화면이 보인다. 외부 팩 제거·누락·오류 뒤 코드 기본값으로 돌아가며 화면 행동은 변하지 않는다. 이 개발용 진입은 아직 진행도·전투 완료를 뜻하지 않는다.

### 5단계: 선택형 웹 보조 도구 판단

- Minecraft 네 화면을 만든 뒤 실제 반복 작업 중 웹 도구의 비용 대비 이득 평가
- 채택할 경우 같은 fixture와 내보낸 컴포넌트·상태·행동 manifest 사용
- `320×240`, `426×240`, `640×360` 논리 뷰포트와 한·영 상태 전환
- 아이템·포켓몬·트레이너 모델은 비권위 대체 슬롯으로만 표시
- CSS와 Minecraft 픽셀 배치의 동등성은 테스트하거나 약속하지 않음

완료 조건: 유지 비용보다 반복 속도 이득이 명확할 때만 도구를 유지하며, 만들지 않아도 제품 단계를 막지 않는다.

### 6단계: 네 화면 실제 월드 승인

- 세 논리 화면 크기의 Minecraft 동일 fixture 캡처 비교
- 기본 owo·바닐라 표면 노출 여부 확인
- 마우스, 키보드, ESC, 포커스, 툴팁, 내레이션과 스크롤 확인
- 3D 모델 슬롯 클리핑과 리소스 재로드 확인
- 프레임 시간과 대형 목록 입력 지연 측정

완료 조건: 빡대리님의 네 화면 시각 승인 뒤 실제 서버 연동으로 진행한다.

## 4. 제품 기능 단계

### 7단계: MBC 공개 서버 계약

- 접근 정책 API와 MBC 단독 기본 허용 테스트
- 모든 Tower·Factory 시작 경로의 서버 측 검사
- 허브 가용 상태와 잠금 사유 페이로드
- 관리형 PvE 배틀 API
- `ResourceSkin` 트레이너 투영
- 원자적 BP 공개 API
- 안정적인 콘텐츠 ID

### 8단계: 애드온 골격과 데이터 로더

- GUI 착수용 최소 모듈을 프로덕션 애드온 골격으로 완성
- 검증된 PokeBadges 대상 버전, 모드 ID와 API를 필수 의존성으로 적용
- 선택 레벨캡 제공자의 선택 의존성
- 서버·클라이언트 초기화와 등록 해제 수명주기
- `modmenu` 진입점, 설정 화면, `ko_kr`·`en_us`
- 버전 있는 JSON 스키마와 원자적 데이터 스냅샷
- 기본 신오 Pt 기반 데이터도 같은 로더로 제공

### 9단계: 진행도와 외부 동기화

- 플레이어별 체육관 승리와 챔피언 상태 저장
- 계급 파생 계산
- PokeBadges 어댑터와 조정 큐
- 선택한 레벨캡 제공자 어댑터
- 로그인·승리·리로드 시 동기화
- 백업과 명시적 관리자 이관 명령

### 10단계: 터미널과 GUI 상태 연결

- 개발용 최소 터미널을 제품 블록 엔티티, 아이템, 조합법, 전리품, 모델과 텍스처로 완성
- 거리·월드·세션·리비전 서버 검증
- fixture 상태를 서버 권위 화면 모델로 교체
- 오래된 상태와 조작 요청 거부
- 사천왕 로비·연속 진행 화면 추가

### 11단계: 체육관 배틀

- 파티 검증과 팀 스냅샷
- MBC 관리형 PvE 시작·정리
- 데이터 정의 상대 팀과 AI 선택
- 리소스 스킨 가상 트레이너
- 승패, 뱃지, 레벨캡, 보상 거래의 멱등 처리

### 12단계: 사천왕 및 챔피언

- 팀·기술·도구 잠금
- 사천왕 4명과 챔피언의 순차 세션
- 전투 사이 기본 완전 회복
- 패배·이탈·재시작 정책 적용
- 챔피언 칭호와 최초 승리 결과

### 13단계: 후반 시설 해금

- League Challenge 접근 정책 등록
- 챔피언 전 Tower·Factory 잠금
- 챔피언 승리 직후 상태 갱신
- GUI, 패킷, 직접 API 우회 테스트
- 애드온 제거 시 MBC 기본 동작 복구

### 14단계: 기본 콘텐츠와 릴리스

- 신오 Pt 기반 8관장, 사천왕, 챔피언 정의
- 현대 Cobblemon용 팀과 보상
- 허가된 기본 스킨·초상화와 크레딧
- 뱃지별 레벨캡과 난이도 플레이테스트
- 전용 서버·실제 클라이언트, 재접속·재시작과 악의적 요청 검증
- 데이터팩·리소스팩 교체와 실패 롤백 검증

## 6. 권장 커밋 단위

1. 실행 순서 후속 결정과 문서 정합성
2. League 최소 모듈, 메타데이터와 개발 환경 전용 GUI 진입점
3. 실험 MbcUI 타입 계약과 검증 테스트
4. League 홈 fixture와 코드 드로잉 Minecraft 스파이크
5. 같은 fixture의 owo 후보 Minecraft 스파이크
6. Cobblemon UI 툴킷 소스 모듈과 Component Gallery
7. 내용 폭·variant·size 기반 위젯과 불변 테마 스냅샷
8. 코드 기본 토큰·내장 테마와 외부 cosmetic 테마 검증
9. 실제 월드 터미널 진입과 League GUI 네 화면 수직 단면
10. Battle UI 행동 메뉴·내레이션·전체 기록의 두 번째 소비자 적용
11. 백엔드·툴킷 배포 방식 결정과 버려지는 스파이크 정리
12. 외부 Visual Pack 예제와 금지 필드·폴백 테스트
13. 선택형 fixture·manifest 웹 보조 도구
14. MBC 접근 정책 API와 Tower·Factory 적용
15. MBC 관리형 PvE·트레이너 외형·BP 공개 API
16. 검증된 PokeBadges 의존성, 데이터 로더와 프로덕션 애드온 골격
17. 진행도·PokeBadges·레벨캡 어댑터
18. 터미널과 서버 권위 GUI 연결
19. 체육관 전투
20. 사천왕·챔피언 연속 도전
21. 시설 해금과 기본 신오 콘텐츠

각 단위는 정확한 파일만 스테이징하고 기존의 다른 작업을 포함하지 않는다.

## 7. 완료 기준

- 화면 구조·행동·확인 단계가 타입 있는 계약에 있으며 리소스팩으로 교체되지 않는다.
- 기본 JAR만으로 화면이 완전하고 선택형 Visual Pack이 허용된 cosmetic 토큰과 시각 자산만 바꾼다.
- 첫 League 홈과 네 화면 수직 단면이 실제 월드의 세 논리 폭, 터미널·패킷, 3D 슬롯, 물리 입력과 접근성 검증을 통과한다.
- 선택형 웹 도구는 fixture·manifest의 의미만 공유하며 Minecraft와 픽셀 동등성을 주장하지 않는다.
- 관장·사천왕·챔피언과 팀·규칙·보상·외형을 데이터·리소스팩으로 교체할 수 있다.
- 터미널 우클릭만으로 전체 도전 흐름을 사용할 수 있고 월드 NPC나 체육관 건물이 필요 없다.
- 계급과 챔피언 상태가 저장 원본에서 일관되게 파생된다.
- PokeBadges와 레벨캡이 재접속·리로드·실패 복구 뒤에도 수렴한다.
- 사천왕과 챔피언이 채택된 연속 도전 규칙대로 동작한다.
- 애드온 설치 시 챔피언 전 Tower·Factory의 모든 새 진입이 잠긴다.
- 애드온이 없을 때 MBC의 기존 기능과 화면이 회귀하지 않는다.
- 빌드뿐 아니라 전용 서버·클라이언트의 실제 UI, 렌더링, 입력, 전투와 우회 방지까지 확인한다.
