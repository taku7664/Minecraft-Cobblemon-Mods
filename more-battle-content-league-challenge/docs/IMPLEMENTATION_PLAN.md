# 구현 계획

## 1. 착수 전 결정 게이트

다음 항목은 코드를 쓰기 전에 확정하거나 실제 환경에서 검증한다.

1. Cobblemon 1.8.1에서 사용할 개인별 레벨캡 모드와 API
2. 뱃지별 정확한 레벨캡 숫자
3. 서버당 단일 활성 리그인지 다중 리그인지
4. 사천왕 연속 도전 중 접속 종료·서버 재시작 처리
5. 연속 도전 중 가방 아이템 사용 규칙
6. 진행 중 Tower·Factory 런에 잠금 정책을 적용하는 시점
7. PokeBadges 대상 버전, 모드 ID, 실제 뱃지 식별자
8. 레벨캡 초과 포켓몬의 경험치·진화·복종·전투 참가 처리 의미

이 항목들을 추측으로 고정하지 않는다. 특히 레벨캡 제공자는 후보 JAR을 실제 개발 프로필에 넣고 API·저장·동기화를 확인한다.

## 2. 단계별 구현

### 1단계: MBC 공개 계약

- 접근 정책 API와 단독 MBC 기본 허용 테스트
- 모든 Tower·Factory 시작 경로의 서버 측 검사
- 허브 가용 상태와 잠금 사유 페이로드
- 관리형 PvE 배틀 API
- `ResourceSkin` 트레이너 투영
- 원자적 BP 공개 API
- 필요 최소한의 GUI 스타일·콘텐츠 ID 계약

MBC 코어에 먼저 실패하는 테스트를 추가하고 구현한다. 애드온을 만들기 위해 MBC 내부 타입을 노출하는 식으로 우회하지 않는다.

### 2단계: 애드온 골격

- Gradle 모듈 `more-battle-content-league-challenge`
- 모드 ID와 패키지 등 README의 네이밍 계약 적용
- Cobblemon, MBC, PokeBadges 필수 의존성 선언
- 선택 애드온의 선택 의존성 선언
- 서버·클라이언트 초기화와 등록 해제 수명주기
- `modmenu` 진입점, 설정 화면, `ko_kr`·`en_us`

### 3단계: 데이터 및 리소스 로더

- 버전 있는 JSON 스키마
- 전체 참조 검증과 원자적 스냅샷 교체
- 기본 신오 Pt 기반 데이터도 같은 로더로 제공
- 리로드 중 진행 세션의 스냅샷 유지
- 관리자 검증·리로드 결과 보고

### 4단계: 진행도와 외부 동기화

- 플레이어별 체육관 승리와 챔피언 상태 저장
- 계급 파생 계산
- PokeBadges 어댑터와 조정 큐
- 선택한 레벨캡 제공자 어댑터
- 로그인·승리·리로드 시 동기화
- 백업과 명시적 관리자 이관 명령

### 5단계: 터미널과 GUI

- 블록, 블록 엔티티, 아이템, 조합법, 전리품, 모델, 텍스처
- 거리·월드·세션·리비전 서버 검증
- 홈, 상세, 파티 확인, 연속 도전, 결과 화면
- 잠금 이유, 내레이션, 키보드 탐색, 번역

### 6단계: 체육관 배틀

- 파티 검증과 팀 스냅샷
- MBC 관리형 PvE 시작·정리
- 데이터 정의 상대 팀과 AI 선택
- 리소스 스킨 가상 트레이너
- 승패, 뱃지, 레벨캡, 보상 거래의 멱등 처리

### 7단계: 사천왕 및 챔피언

- 팀·기술·도구 잠금
- 사천왕 4명과 챔피언의 순차 세션
- 전투 사이 기본 완전 회복
- 패배·이탈·재시작 정책 적용
- 챔피언 칭호와 최초 승리 결과

### 8단계: 후반 시설 해금

- League Challenge 접근 정책 등록
- 챔피언 전 Tower·Factory 잠금
- 챔피언 승리 직후 상태 갱신
- GUI, 패킷, 직접 API 우회 테스트
- 애드온 제거 시 MBC 기본 동작 복구

### 9단계: 기본 콘텐츠와 밸런스

- 신오 Pt 기반 8관장, 사천왕, 챔피언 정의
- 현대 Cobblemon용 팀과 보상
- 허가된 기본 스킨·초상화와 크레딧
- 뱃지별 레벨캡과 난이도 플레이테스트

### 10단계: 릴리스 검증

- 단위·계약·통합 테스트
- MBC 단독, 필수 의존성 포함, 선택 애드온 조합 로드 테스트
- 전용 서버와 실제 클라이언트 접속
- 터미널 GUI, 렌더링, 전투, 재접속, 서버 재시작 검증
- 악의적 패킷과 중복 결과 재전송 검증
- 데이터팩·리소스팩 교체와 실패 롤백 검증

## 3. 핵심 테스트 행렬

| 영역 | 필수 사례 |
| --- | --- |
| 계급 | 0–2, 3–4, 5–7, 8개, 챔피언의 경계값 |
| 체육관 | 순서 잠금, 레벨 위반, 승리·패배, 중복 결과 |
| 뱃지 | 지급 성공, 외부 실패 후 재조정, 수동 제거 |
| 레벨캡 | 로그인·승리·리로드 동기화, 공급자 오류 |
| 연속 도전 | 5연승, 각 구간 패배, 회복, 이탈, 재시작 |
| 시설 잠금 | GUI, 조작 패킷, 직접 API, 애드온 부재 |
| 외형 | default/slim, 누락 스킨, 리소스 리로드, 정리 |
| 데이터 | 중복 ID, 누락 참조, 잘못된 순서, 원자적 롤백 |
| 보상 | 최초·반복, BP 중복 지급 방지, 저장 실패 |

## 4. 커밋 단위

구현은 다음과 같이 독립적으로 검토 가능한 단위로 나눈다.

1. MBC 접근 정책 API와 테스트
2. MBC Tower·Factory 적용과 허브 상태
3. MBC 관리형 PvE 및 트레이너 외형 API
4. MBC BP 공개 계약
5. League Challenge 모듈 골격
6. 데이터 로더와 기본 빈 스키마
7. 진행도·PokeBadges·레벨캡 어댑터
8. 터미널과 GUI
9. 체육관 전투
10. 사천왕·챔피언 연속 도전
11. 시설 해금과 기본 신오 콘텐츠

각 단위는 정확한 파일만 스테이징하고 기존의 다른 작업을 포함하지 않는다.

## 5. 완료 기준

- 관장·사천왕·챔피언과 팀·규칙·보상·외형을 데이터/리소스팩으로 교체할 수 있다.
- 터미널 우클릭만으로 전체 도전 흐름을 사용할 수 있고 월드 NPC나 체육관 건물이 필요 없다.
- 계급과 챔피언 상태가 저장 원본에서 일관되게 파생된다.
- PokeBadges와 레벨캡이 재접속·리로드·실패 복구 뒤에도 수렴한다.
- 사천왕과 챔피언이 채택된 연속 도전 규칙대로 동작한다.
- 애드온 설치 시 챔피언 전 Tower·Factory의 모든 새 진입이 잠긴다.
- 애드온이 없을 때 MBC의 기존 기능이 회귀하지 않는다.
- 빌드뿐 아니라 전용 서버·클라이언트의 실제 UI, 렌더링, 전투, 우회 방지까지 확인한다.
